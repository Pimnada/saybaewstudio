# การสำรองข้อมูล saybaewstudio

```bash
php tools/backup.php            # สำรองใหม่ + ลบไฟล์เก่าเกิน 30 ชุด
php tools/backup.php --list     # ดูว่ามีอะไรเก็บไว้บ้าง
php tools/backup.php --verify   # อ่านไฟล์ล่าสุดกลับมาตรวจว่ายังใช้กู้ได้
```

ไฟล์เก็บที่ `../backups/saybaewstudio/` — **นอก repo และนอก web root**

---

## ทำไมไม่เอาทุกอย่างขึ้น git

git เก็บทุกอย่างไว้ตลอดกาล ลบไฟล์ใน commit ทีหลังก็ยังอยู่ใน history และใครที่เคย
clone ไปแล้วก็ได้ไปครบ สามอย่างนี้จึงไม่ควรอยู่ใน git เด็ดขาด

| | เหตุผล |
|---|---|
| `config.php` | รหัสฐานข้อมูล production และ hash รหัสผ่านแอดมิน — หลุดแล้วต้องเปลี่ยนทั้งชุด |
| `public/uploads/` | **รูปเด็กของลูกค้า** เป็นข้อมูลของบุคคลอื่น และหนักเป็นกิกะไบต์ |
| `dev.sqlite` | ฐานข้อมูลจริงตอนพัฒนา รวมชื่อและเบอร์โทรลูกค้า |

แบ่งหน้าที่ให้ชัด — **โค้ดอยู่ใน git · ข้อมูลอยู่ใน backup** และไม่ปนกัน

## สิ่งที่สคริปต์ทำ

**`db_<วันเวลา>.sql.gz`** — dump ทั้งฐานข้อมูล ทั้ง schema และข้อมูล เขียนแบบสตรีมทีละแถว
เพราะตาราง `photos` โตถึงหลักแสนแถวได้ ถ้าดึงเข้า array ทีเดียวจะกิน memory จนล่ม

**`files_<วันเวลา>.txt.gz`** — รายการไฟล์รูปทุกไฟล์พร้อมขนาดและ md5 **ไม่ใช่ตัวรูป**
เพราะสำเนาอัลบั้ม 100 GB วันละชุดเป็นเวลาหนึ่งเดือนไม่ใช่การสำรองข้อมูล แต่คือการถมดิสก์
รายการนี้บอกได้ว่าหลังกู้คืนแล้วไฟล์ไหนหายไปบ้าง

เก็บย้อนหลัง 30 ชุด แล้วลบของเก่าทิ้งอัตโนมัติ · ไฟล์ตั้ง `chmod 600`

## ตัวรูปสำรองยังไง

`public/uploads/` ต้อง rsync แยกไปที่เก็บอื่น ไม่ใช่ผ่านสคริปต์นี้

```bash
rsync -az --delete ~/Sites/saybaewstudio/public/uploads/ /Volumes/Backup/saybaewstudio-uploads/
```

> `--delete` ตรงนี้ปลอดภัยเพราะปลายทางเป็น**ที่เก็บสำรอง** ไม่ใช่เซิร์ฟเวอร์
> อย่าเอา `--delete` ไปใส่ใน `deploy.sh` เด็ดขาด

## ตั้งให้ทำอัตโนมัติ

```bash
crontab -e
```

เพิ่มบรรทัดนี้ — สำรองทุกวันตีสอง

```
0 2 * * * cd /Users/pimnada/Sites/saybaewstudio && /usr/bin/env php tools/backup.php >> /tmp/sbs-backup.log 2>&1
```

บนเซิร์ฟเวอร์ Cloudways ใช้ path ของแอปแทน และตั้งใน **Application Management → Cron Job Management**

## backup ที่ไม่เคยลองกู้ ไม่ใช่ backup

`--verify` อ่านไฟล์ล่าสุดกลับมาจริง นับจำนวนตารางและแถว แล้วบอกว่าใช้ได้หรือไม่
ควรรันเดือนละครั้งเป็นอย่างน้อย

วิธีกู้คืนจริง

```bash
gunzip -c backups/saybaewstudio/db_2026-08-19_020000.sql.gz | mysql -u USER -p DBNAME
```

## เว็บอื่นในเครือ

สคริปต์นี้เขียนให้ saybaewstudio แต่โครงเดียวกันใช้กับ tobwai, sorndekcoding,
laaklaai และ maeranie2022 ได้ — เปลี่ยนแค่วิธีเชื่อมฐานข้อมูลตอนต้นไฟล์

**ยังไม่ได้ตั้งให้เว็บเหล่านั้น** เพราะการเพิ่ม cron บนเซิร์ฟเวอร์ที่ให้บริการอยู่จริง
ควรทำตอนมีคนดูผลรันครั้งแรก ไม่ใช่ตั้งทิ้งไว้แล้วหวังว่าจะทำงาน
